最新状态：已获授权完成首次真实Judge校准，15/16整例匹配但触发关键错误，正式14题与Reader未执行。见 [真实执行报告](EVAL_PHASE3_REAL_MODELS.md) 和 [最终简历材料](EVAL_RESUME_FINAL.md)。下文第一、二阶段零费用等表述均属于对应历史阶段。

本文主体保留第一阶段结果，第二阶段诊断与面试表述补充在末节。本项目验证的是 governed 路径；当前默认部署为 mem0_primary，不要将两条路径的能力与成绩混写。第一阶段数据以 [原始报告](../evals/reports/2026-11-06-local-v3/report.md) 和逐题 JSON 为准，后续以 [第二阶段报告](EVAL_PHASE2.md) 为准。

## 为什么这样设计

长期记忆要经历“形成→治理→找回→回答”，只测最终 QA 无法区分是未记住、记错、找不到、找到了旧版本，还是 Reader 不会使用证据。因此拆分四类任务，并保留逐题结果，把问题定位到具体阶段。

检索先把同一份事实灌入同一隔离库，避免不同 Formation 质量污染检索比较；自建 QA 则从自然语言开始，真实执行规则提取、Candidate 写入、检索、Context Pack 和抽取式回答。两者目的不同。公开 LongMemEval 对照是保留全部历史的原文分块，明确没有评测生产 LLM 提取。

实验使用真实 Repository/BM25/RRF/TransparentReranker/Context Pack，不复制一套生产治理逻辑。外部向量服务不在本地离线验证范围，使用 TF-IDF cosine 作为透明控制组，并明确其不是语义 embedding。模型调用和费用上限均为 0，不能拿离线控制组成绩宣传云模型效果。

单路召回 20，混合每路 10，总名额相同；混合重排复用同一候选预算。这样能解释比较中的计算投入。该合同仍不意味着 CPU/SQL/重排成本完全相同，所以另报延迟；同预算也不能消除不同候选来源的相关性偏差。

规则、参数和样本先确定，再运行；公开题目按种子和题型选取，不按成功率筛选。评测中的统计误差、人工标签偏差、基础模型训练污染不能靠固定种子消除。

## 指标的含义与计算

| 指标 | 计算方法 | 解释 |
|---|---|---|
| Recall@k | 每题 `前 k 个唯一结果中的相关结果数 / 全部相关结果数`，再对题目求均值 | 多证据题衡量覆盖；两条证据的题 @1 最高只有 0.5，不等于 Hit@1 |
| MRR@10 | 第一条相关结果排在 r≤10 时为 1/r，否则 0，再求均值 | 衡量首条有用结果的位置，不反映剩余证据是否齐全 |
| nDCG@10 | `DCG/IDCG`；DCG=`Σ(2^rel_i−1)/log2(i+1)`，i 从 1 开始；IDCG 为全部标签按相关性降序排列后的前 10 个理想增益 | 必须累计所有相关结果并归一化，不能只算首条命中折扣 |
| P50/P95 | 排序后在线性插值位置 `(n−1)×p` 取分位数 | 本地实际 time-to-result/time-to-error；触及 SQL 上限时另看成功查询 P95 与错误数 |
| Formation Precision | TP/(TP+FP) | 输出事实中正确的比例；重复及额外错误事实计 FP |
| Formation Recall | TP/(TP+FN) | 应当形成的事实中找回多少 |
| Formation F1 | 2TP/(2TP+FP+FN) | 使用跨题累加的 micro P/R/F1；最大二分匹配保证候选和事实一对一 |
| Answer Accuracy | 正确回答题数/全部 QA 题数 | 当前为 Unicode/大小写/标点归一化后的精确答案别名匹配；拒答题只有明确拒答才算对 |
| 拒答正确率 | 无法回答题中正确拒答数/无法回答题数 | 单列分母，不能靠多加负例提升总 Accuracy；超时不算正确拒答 |
| 旧事实错误率 | 具有旧事实标注的题中，回答命中旧事实字符串的题数/该类题数 | 当前是自动诊断规则，不是通用语义事实核查；没有该类题时为 null |
| Retrieval Hit | 返回结果中是否有标注相关文档/会话 | 与 Answer Accuracy 分开；命中会话不代表检索块一定含充分证据 |

Precision/Recall 等分母为零时使用 null，不伪造 100%。无证据的拒答题不进入正例 Recall/MRR/nDCG 分母。

自建检索的 3 轮用于测延迟；独立题数仍为 36。公开 12 题中含拒答题，不能把 12×4 方法计作 48 个独立问题，也不能据此得出统计显著性结论。

## 真实结果及其边界

自建 40 文档/36 查询上，BM25 和 TF-IDF 的 Recall@5 均为 94.44%；Hybrid 同为 94.44%，Hybrid+TransparentReranker 为 93.06%。这组数据不支持“加入重排一定提升效果”，反而暴露透明过滤器可能丢相关候选。不能据此证明 TF-IDF 优于真实语义模型，因为本轮没有运行语义模型。

24 个自然语言 Formation 样例上，本地规则基线 TP=10、FP=3、FN=6，Precision=76.92%、Recall=62.50%、F1=68.97%。16 题自建 QA 的严格 Answer Accuracy=81.25%，其中 12 道可回答题为 75%，4 道拒答题为 100%。这些是小样本规则基线成绩，不是生产 LLM 的效果。

另有两道动态更新/遗忘 QA：旧事实错误 0/2。治理的 11 个探针断言符合预期，其中一个专门复现“普通同义改写进入 contested”的缺口，不能说 11 项能力全部通过。相同旧候选的 Head 闸门消融中，直接信任候选会保留 1 条旧事实，canonical 授权保留 0 条；这证明了该场景的闸门作用，不是自然语言错误率下降的统计实验。

LongMemEval-S 接入固定 12 题公开子集，保留干扰会话，逐题结果、超时和源文件哈希均可核对。没有运行官方 LLM judge，所以本地严格 EM 不能与官方榜单 Accuracy 对比。公开长历史还暴露了 BM25 聚合重复执行和超时，详见 [性能证据](EVAL_PERFORMANCE.md)。不应隐去超时后只展示成功题。

这 12 题包括 10 道可回答题和 2 道拒答题。TF-IDF 会话 Recall@5=85%、MRR@10=0.85，可回答题的会话命中率为 90%，但严格回答准确率为 0/10；仅两道拒答正确，总 Accuracy=2/12。BM25/Hybrid/Hybrid+Rerank 分别有 9/9/7 次 SQL 超时。每组独立执行会受到计划缓存与负载影响，不能把这组超时差异归因为重排质量提升。

公开历史共 9767 块，实际索引 9755 块；12 块被输入规则拒绝（5 块格式/控制字符、4 块注入规则、3 块秘密样式规则），另有 14 块脱敏。题目分母没有删除，所有方案使用相同的成功写入语料。这说明 Adapter 已能跑通完整子集，但仍有输入规范化和模型理解方面的改进空间。

已有证据能证明：评测合同可执行、评分公式有回归测试、隔离 PG 上的指定状态转移与检索闸门可验证、失败能追溯。本轮不能证明生产并发容量、SLO、所有语义改写去重、真实模型泛化、全部身份组合安全、外部索引可靠性，以及备份/WAL/第三方副本的物理删除。

## 面试官可能追问的 10 个问题

1. **为什么 Recall@1 低于 MRR，而多证据题 @1 不能达到 1？** Recall 按相关文档总量归一化；MRR 只看首条相关结果。两个指标回答不同问题。
2. **你如何确认 nDCG 实现正确？** 用手算多相关、分级标签、理想顺序、空结果和 @10 边界做测试；旧实现缺少 IDCG，只在单相关场景下近似正确。
3. **这次 Vector 是什么模型？为什么不用已有语义服务？** 实际是 corpus-only TF-IDF，不是神经语义模型。选择它是为了零模型成本先建立可运行基准；真实 embedding 与 neural rerank 必须另行验证。
4. **混合和重排为何没有明显收益？** 数据量小、词法特征相关，RRF 可能放大共同偏差，透明重排还会阈值过滤。先检查失败样例，不能仅凭算法名字宣布提升，也不在这份测试集上反复调阈值。
5. **如何防止 LongMemEval 泄漏答案？** Adapter 将输入与标签分开，不读取 has_answer 来筛历史，保留所有角色/干扰会话，预测器只看问题和 Context Pack；测试故意放置金答案哨兵，确认不会进入导入对象。这不等于排除了模型预训练污染。
6. **检索命中而回答错误，怎么定位？** 先检查 Formation 是否保存事实，再检查召回/排序/会话证据，接着看预算后的 Context Pack，最后看 Reader。公开对照中的单句 Reader 不擅长跨会话或时间推理，严格 EM 也不接受所有合理改写。
7. **语义去重和冲突治理有什么不同？** 同一 scope/type/key 下的相同规范内容会复用 Version 并追加来源；不同内容进入 contested。普通改写若未被提取器规范化，就可能被误作冲突；本轮明确测出了这个缺口。
8. **异步投影没更新时，旧事实会不会泄漏？** 索引只提供候选，canonical Head/revision/hash/权限决定是否可读；本轮在投影清理前复用旧候选验证了拦截，Context Pack 消费也会检查状态。
9. **BM25 超时为什么不直接加索引？** 先用相同绑定参数和真实计划定位：原统计聚合可重复 340 次；新租户估算 1 块而实际 827 块，长度查询发生约 4716 万次 join-filter 排除。第二阶段仅物化全局统计、按版本复用已有索引计算 MAX 长度，保留公式和缓存，用独立数学参考及修复前后排名证明没有改变排序质量。
10. **如何解释零费用和“可复现”？** Runner 不含在线模型调用入口，模型调用/费用上限就是零；记录 seed、源数据 SHA、源码 SHA、锁文件、PG 镜像、参数和逐题结果。排名和本地质量可核对，延迟/超时仍受硬件、执行计划和负载影响，不保证逐毫秒相同。

## 第二阶段补充：如何解释诊断与优化

Oracle Evidence 直接给正确证据，能把“找不到”与“不会回答”分开；identity scorer control 直接给金答案，能检查标签映射与评分函数。后者 10/10 不是系统成绩，前者原规则 Reader 严格 EM 仍为 0/10，也不等于所有回答在语义上均错误。正确实体包含在完整句子中、短 Yes 参考与完整事实陈述、偏好 rubric，均需要适当的评分合同。我们没有修改原答案或放宽主评分。

会话 Recall@5=85% 可以与 QA 0/10 同时成立：命中相关会话不保证选中具体 turn，多个证据还可能被 Context 预算整块省略；单句规则也不能自动完成加法或时间比较。修复了 raw cosine 直接过相关性阈值的 Adapter 错误，仍保留真实 LLM 和官方 judge 待验证的边界。

性能结果来自同一临时 PG 的固定历史长度/查询对照，不是生产 SLO。801 块 auto 组是两类查询各三次：请求 P95 约 3048→200 ms，旧 SQL 3/6 超时，最终 0/6。小语料 P50 没有明显改善；关闭缓存的中间方案仍有公开长历史超时，因此最终保留缓存并修复长度计算的计划敏感性。

新增 195 文档/24 查询的工程留出集没有与旧集重复的文档或问题，但仍由同一开发者编写；20 正例不足以宣布统计显著优越，4 无答案查询均有检索命中更暴露了拒答判定的必要性。三次重复只是延迟重复，不是样本量翻倍。16 个 PG 集成测试实际运行后首次 15/16，定位出重复冲突与唯一索引不一致；最小修复后 16/16，不能把原来的跳过算通过。

## 第三阶段：如何解释真实模型实验协议

本节主体保留协议及离线诊断结果。现已执行真实Judge校准，但关键错误未通过，正式Reader与14题测试仍未运行；实际状态以 [真实执行报告](EVAL_PHASE3_REAL_MODELS.md) 为准。原准备数据入口见 [第三阶段报告](EVAL_PHASE3_PREPARATION.md)。

**为什么使用BM25+Vector？** BM25擅长名字、编号、精确词项；学习到的向量可能找回词面不同的表达。这里的Vector必须是有明确revision和维度的真实模型，TF-IDF只作控制组。融合不会自动解决时间冲突、旧事实或权限；最终仍要经canonical Head/Scope授权。

**什么情况下Hybrid更好？** 两个通道分别找回对方遗漏的相关证据，而且噪声增加不足以挤出正确证据时。必须看逐题候选、交并集、R@K/MRR/nDCG和预算；不能在一个通道20条、另一个混合40条时把收益都归因于算法。当前协议单路20、混合每路10，总预算相同；固定RRF参数，不看锁定测试答案调权重。

**什么时候Rerank不值得增加？** 召回中没有正确证据时，重排不能凭空产生它；候选已很好时可能只增加模型延迟；过滤阈值也可能丢证据。第二阶段透明重排在开发集Evidence Recall@5为55%，TF-IDF为66.67%；透明规则不代表神经重排模型。真实Reranker必须另测边际质量、尾延迟、模型调用和失败成本，当前不填它的成绩。

**为什么Recall高而QA低？** 会话命中只是第一个层次。旧12题TF-IDF Session Recall@5=85%，标记证据块Recall@5=66.67%、Context标记字符覆盖约67.16%；后两个指标是has_answer代理，不能混写为人工事实覆盖6/10。随后还可能失败在算术/时间推理、拒答或评分合同。Oracle和identity scorer control分别检查证据充分时的Reader、金答案与评分映射，而不是给系统加分。

**怎样设计Context预算和截断？** 先定Reader总输入/输出界，再为系统提示、问题、时间及来源ID留空间；在统一排序和canonical授权后打包，最后至多截一个前缀并记录其余遗漏。每个模型的tokenizer与provider usage分开。当前比较采用评测内rank-only策略，不能声称生产0.4相关性阈值已被新模型验证；不能按测试题答案选择块。

**Formation、Retrieval、Reader分别怎么测？** Formation用自然语言输入和一对一事实标注算micro P/R/F1，重复输出算FP；Retrieval预先固定相同事实语料，测会话和证据块召回/排序；Reader使用相同Prompt/模型，比较Oracle和实际检索，记录正确性、拒答与证据支持。公开原历史分块RAG绕过了真实LLM Formation，不能宣传为完整事实提取质量。

**怎样评估更新、冲突和遗忘？** 操作后断言DB的Version/Head、来源、审核和删除状态，再用旧候选与新检索验证可见性。已有待审事实的新冲突返回409且事务回滚，调用方应先解决审核。RLS非超级用户测试和Head过滤只证明被测组合；逻辑不可见不等于WAL、备份和第三方副本物理擦除。

**怎样用Benchmark指导工程优化？** 先锁协议和未见样本，拆检索、Context、回答与评分的错误，不按总分猜根因。第二阶段用实际计划定位统计重复和长度连接；第三阶段138次性能测量又把重启与热池分开，并用6次桥重建证明约804ms来自探针分词器初始化。后续分块、阈值和模型选择在开发集做，冻结后再测独立14题；不把硬件/布局差异当作一次新优化收益。

## 真实Judge校准后的面试结论

本次使用冻结V3和SiliconFlow DeepSeek-V3.2，完成2次可用性检查及16次校准。15/16整例一致，但partial_answer触发关键错误；系统按协议阻止正式14题测试，没有改标签、改Prompt或重试到通过。

**为什么15/16仍停止？** 15/16只是一般一致率要求，关键错误0是独立要求。将31/32标签一致或93.75%整体一致拿来替代关键门禁，会掩盖评分维度混淆。关键门禁在真实调用中生效，是本次能证明的工程行为；不能据此宣称Judge具有稳定泛化能力。

**真实Reader和Oracle能证明什么？** 本次未执行，不能证明任何正式QA、拒答或幻觉效果。正式质量字段保持null，不填0%，也不拿历史工程集替代公开测试结果。校准评分的是人工提供回答，不是Reader新生成的回答。
