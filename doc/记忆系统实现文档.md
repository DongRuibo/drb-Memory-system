# 记忆系统实现文档

> **状态：历史设计输入，非当前实现规范。** 本文保留早期方案与调研上下文；其中 `extract_and_store`、可变 `memory_records`、可选字段组合 Scope、把安全/权限约束放入 Memory Context 等内容已被修订。开发请从 [`docs/README.md`](../docs/README.md) 开始，并以已接受 ADR、OpenAPI 和编号规范为准。

> 适用范围：Rust Agent 产品、Mem0 OSS 自部署、PostgreSQL + pgvector、两人开发团队  
> 文档目标：指导 POC、MVP 和生产化实现，并明确 Mem0 与自研 Memory Service 的职责边界

---

## 1. 项目目标

本项目需要为 Agent 提供跨会话长期记忆能力，使 Agent 能够：

- 记住用户明确表达的长期偏好；
- 记住稳定的用户信息和项目事实；
- 在后续任务中检索相关记忆；
- 对错误记忆进行修正和删除；
- 控制哪些记忆可以进入本次模型上下文；
- 保证用户、项目和租户之间的数据隔离；
- 保留来源、版本、状态和审计记录；
- 在未来可以替换 Mem0，而不重写 Agent Runtime。

第一阶段采用：

```text
Rust Agent Runtime
        ↓
Rust Memory Service
        ↓
Mem0 Adapter
        ↓
Mem0 OSS
        ↓
PostgreSQL + pgvector
```

## 2. 核心设计原则

### 2.1 Mem0 不是最终权威数据源

Mem0 负责：

- 记忆提取；
- 基础去重；
- Embedding；
- 检索；
- 可选 Reranker；
- Provider 内部的数据管理。

Rust Memory Service 负责：

- 是否允许写入；
- 租户、用户、项目和 Agent Scope；
- 记忆状态；
- 来源；
- 版本；
- 有效时间；
- 权限；
- 审计；
- Context 组装；
- 最终是否允许记忆影响 Agent。

PostgreSQL 中的 `memory_core` 数据是业务权威记录。

Mem0 中的数据应被视为：

> 可替换、可重建的智能处理层和检索投影。

---

### 2.2 模型只能提出候选，不能直接修改正式状态

推荐链路：

```text
用户消息 / 工具结果 / 任务结果
              ↓
Mem0 提取或外部提取器
              ↓
Memory Candidate
              ↓
Rust Policy 校验
              ↓
Accepted / Rejected / Needs Review
              ↓
正式 Memory Record
```

对于低风险偏好，可以自动接受。

对于以下内容，应进入审核或更严格的规则：

- 身份和权限信息；
- 企业关键事实；
- 涉及其他用户的信息；
- 程序记忆；
- 来源不清楚的推断；
- 与已有记忆冲突的内容；
- 可能影响真实操作的约束。

---

### 2.3 State、Memory 和 Context 必须分开

```text
State：
当前任务正在执行什么。

Memory：
跨任务、跨会话长期保存的信息。

Context：
本次模型调用实际看到的信息。
```

示例：

```text
“当前任务执行到第 3 步”
→ Runtime State

“该项目要求使用 Node 20”
→ Long-term Memory

“本次调用注入了 Node 20 约束”
→ Context Pack
```

不要把当前任务状态直接写入长期记忆。

---

### 2.4 所有第三方能力必须经过 Adapter

业务层不能直接依赖：

- Mem0 的 ID；
- Mem0 的请求结构；
- Mem0 的过滤格式；
- Mem0 的返回字段；
- Mem0 的数据库表。

业务层只认识自己的领域模型。

## 3. MVP 范围

### 3.1 第一版必须实现

- `remember`：提交事件并产生记忆候选；
- `recall`：检索相关记忆；
- `correct`：修正已有记忆；
- `forget`：逻辑删除记忆；
- `get_context`：生成本次 Agent 使用的 Context Pack；
- `inspect`：查看记忆详情、来源和状态；
- 用户、项目、租户隔离；
- 基础记忆版本；
- 来源记录；
- 审计日志；
- PostgreSQL 持久化；
- Mem0 OSS 自部署接入；
- 超时、重试和降级；
- 基础评测集。

### 3.2 第一版暂不实现

- 完整时序知识图谱；
- Graphiti；
- 复杂 Temporal Reasoning；
- 自动 Reflection；
- 自动程序记忆晋升；
- 高级 Memory Decay；
- 多区域高可用；
- 独立向量数据库；
- 多 Agent 共享写入冲突自动合并；
- 模型自动修改正式 Memory Record。

## 4. 总体架构

```mermaid
flowchart TD
    A[Conversation / Tool / Task Events] --> B[Rust Memory API]
    B --> C[Write Policy]
    C --> D[Mem0 Adapter]
    D --> E[Mem0 OSS]
    E --> F[Provider Result]
    F --> G[Memory Candidate]
    G --> H[Validation / Conflict Check]
    H --> I[(memory_core PostgreSQL)]
    I --> J[Retrieval Service]
    J --> D
    J --> K[Context Assembler]
    K --> L[Context Pack]
    L --> M[Agent Runtime]

    I --> N[Audit / Usage Receipt]
    I --> O[Background Worker]
```

## 5. 组件职责

## 5.1 Rust Memory API

对 Agent Runtime 提供统一接口，隐藏 Mem0 的实现细节。

职责：

- 请求认证；
- 参数校验；
- Scope 注入；
- 幂等键生成；
- 调用 Application Service；
- 统一错误码；
- 审计入口；
- OpenAPI 文档。

推荐技术：

- Axum；
- Tokio；
- Serde；
- SQLx；
- Reqwest；
- Tracing；
- thiserror / anyhow。

---

## 5.2 Memory Application Service

负责完整业务流程编排。

核心服务：

```text
RememberService
RecallService
CorrectionService
ForgetService
ContextService
InspectionService
```

它不直接依赖 Mem0 HTTP Client，而依赖 `MemoryProvider` Trait。

---

## 5.3 Memory Policy

负责确定性规则。

包括：

- 哪些事件允许进入记忆提取；
- 哪些类型允许自动接受；
- 哪些内容不应长期保存；
- 冲突时如何处理；
- 哪些 Scope 可以检索；
- 哪些记忆允许进入 Context；
- 是否需要人工审核；
- Retention 和过期规则。

第一版可以采用规则优先、模型辅助的方式。

---

## 5.4 Mem0 Adapter

职责：

- 将内部请求转换为 Mem0 请求；
- 将 Mem0 结果转换为内部领域模型；
- 处理认证；
- 超时和重试；
- 记录 Provider 延迟；
- 屏蔽 OSS 与官方 Platform 的接口差异；
- 屏蔽 Mem0 版本升级差异；
- 保存 `provider_memory_id` 映射。

建议根据自部署实例公开的 OpenAPI 文档生成或校验客户端，不在业务层硬编码第三方接口路径。

---

## 5.5 Memory Repository

负责 `memory_core` Schema 的数据库访问。

Repository 不处理业务规则，只负责：

- 查询；
- 插入；
- 更新；
- 事务；
- 乐观锁；
- 分页；
- 数据库错误转换。

---

## 5.6 Context Assembler

负责将检索结果转换为模型可以使用的上下文。

主要功能：

- Scope 二次过滤；
- 状态过滤；
- 版本过滤；
- 去重；
- Token 预算；
- 记忆类型配额；
- 来源标记；
- 注入顺序；
- 生成 Context Pack；
- 保存 Usage Receipt。

---

## 5.7 Background Worker

负责不适合阻塞主请求的任务：

- Provider 同步重试；
- 缺失索引修复；
- 过期状态更新；
- 物理删除；
- 数据一致性扫描；
- Outbox 事件消费；
- 评测任务；
- 后续 Consolidation；
- 后续 Reflection。

## 7. 领域模型

## 7.1 MemoryScope

```rust
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct MemoryScope {
    pub tenant_id: String,
    pub user_id: Option<String>,
    pub project_id: Option<String>,
    pub agent_id: Option<String>,
}
```

规则：

- `tenant_id` 必填；
- 用户记忆需要 `user_id`；
- 项目记忆需要 `project_id`；
- 检索时不能由客户端任意覆盖 Scope；
- Scope 应从认证上下文和任务上下文中生成。

```rust
    Superseded,
```

说明：

- `Active`：当前可以使用；

## 9.1 提交记忆事件

```http
POST /v1/memory/events
```

请求：

```json
{
  "event_id": "evt_123",
  "source_type": "conversation_message",
  "content": "以后技术问题先讲原理，再讲代码。",
  "occurred_at": "2026-07-27T10:00:00Z",
  "scope": {
    "project_id": "agent-platform"
  },
  "metadata": {
    "conversation_id": "conv_1",
    "message_id": "msg_9"
  }
}
```

注意：

- `tenant_id` 和 `user_id` 不应完全信任请求体；
- 服务端从认证信息中补充；
- `event_id` 作为幂等依据之一。

响应：

```json
{
  "request_id": "req_123",
  "candidate_ids": ["candidate_1"],
  "status": "accepted"
}
```

## 9.4 修正记忆

```http
POST /v1/memory/{logical_id}/correct
```

请求：

```json
{
  "new_content": "当前项目使用 PostgreSQL，不再使用 MySQL。",
  "reason": "用户明确纠正",
```

处理：

```text

→ 旧版本标记 Superseded
→ 新版本标记 Active
→ 同步 Provider
→ 写审计
```

## 9.5 遗忘记忆

```http
DELETE /v1/memory/{logical_id}
```

第一阶段默认逻辑删除：

```text
MemoryStatus = Forgotten
```

同时：

- Context 不再注入；
- 搜索结果被过滤；
- 产生 Provider 删除 Outbox；
- 保留最小审计记录；
- 后续后台任务执行物理清理。

## 10. MemoryProvider Trait

```rust
#[async_trait]
pub trait MemoryProvider: Send + Sync {
    async fn extract_and_store(
        &self,
        request: ProviderRememberRequest,
    ) -> Result<ProviderRememberResult, ProviderError>;

    async fn search(
        &self,
        request: ProviderSearchRequest,
    ) -> Result<Vec<ProviderMemoryHit>, ProviderError>;

    async fn update(
        &self,
        request: ProviderUpdateRequest,
    ) -> Result<(), ProviderError>;

    async fn delete(
        &self,
        request: ProviderDeleteRequest,
    ) -> Result<(), ProviderError>;

    async fn health_check(
        &self,
    ) -> Result<ProviderHealth, ProviderError>;
}
```

第一版允许 Mem0 同时执行提取和内部存储。

生产加固阶段可以调整为：

```text
Mem0 提取
→ Rust Candidate
→ Rust 接受
→ 再同步到 Mem0 索引
```

后者治理更严格，但开发成本更高。

## 11. 写入流程

## 11.1 正常写入

```mermaid
sequenceDiagram
    participant R as Agent Runtime
    participant M as Rust Memory Service
    participant P as Policy
    participant A as Mem0 Adapter
    participant O as Mem0 OSS
    participant D as PostgreSQL

    R->>M: submit event
    M->>D: insert source + idempotency check
    M->>P: pre-write policy
    P-->>M: allow extraction
    M->>A: extract_and_store
    A->>O: provider request
    O-->>A: provider memories
    A-->>M: normalized result
    M->>P: candidate validation
    P-->>M: accept / reject / review
    M->>D: transaction save candidate/record/outbox
    M-->>R: result
```
Agent Runtime 把一条事件交给 Rust Memory Service；Rust 先做来源和策略检查，再调用 Mem0 提取记忆；最后由 Rust 决定接受、拒绝还是人工审核，并把正式结果写入 PostgreSQL。

---

## 11.2 写入前规则

不应提交给 Mem0：

- 纯问候；
- 明显临时状态；
- 密码、Token 和密钥；
- 未授权的第三方个人信息；
- 当前任务的中间步骤；
- 大段原始工具日志；
- 可以从 Canonical State 直接读取的数据；
- 重复心跳和系统事件。

第一版启发式规则：

```text
明确偏好表达
→ 高优先级

长期项目约束
→ 高优先级

包含“以后、从现在开始、一直、长期”
→ 提高长期记忆概率

包含“今天、此刻、临时、先”
→ 降低长期记忆概率

工具原始输出
→ 默认不直接记忆

任务最终验证结果
→ 可生成 Episodic Candidate
```

---

## 11.3 冲突处理

示例：

```text
旧记忆：项目使用 MySQL
新信息：项目已经迁移到 PostgreSQL
```

第一版规则：

1. 根据 `normalized_key` 查找当前 Active 记忆；
2. 判断是否是同一逻辑事实；
3. 如果内容一致，忽略或增加来源；
4. 如果是明确更新：
   - 创建新版本；
   - 旧版本标记 `Superseded`；
   - 新版本标记 `Active`；
5. 如果无法判断：
   - 新旧两条标记 `Contested`；
   - 不自动进入 Context；
   - 进入人工审核或后续解决流程。

## 12. 检索流程

```mermaid
sequenceDiagram
    participant R as Agent Runtime
    participant M as Rust Memory Service
    participant A as Mem0 Adapter
    participant O as Mem0 OSS
    participant D as PostgreSQL
    participant C as Context Assembler

    R->>M: recall(query, scope)
    M->>D: load active constraints
    M->>A: provider search
    A->>O: search
    O-->>A: provider hits
    A-->>M: normalized hits
    M->>D: map provider ids to canonical records
    M->>M: scope/status/version filters
    M->>M: deduplicate and rank
    M->>C: compile context
    C->>D: save usage receipts
    C-->>R: Context Pack
```

---

## 12.1 检索前过滤

调用 Provider 前至少确定：

- tenant；
- user；
- project；
- agent；
- memory type；
- 最大结果数；
- 是否包含历史版本；
- 时间范围。

---

## 12.2 检索后二次过滤

即使 Provider 已经过滤，Rust 仍必须再次检查：

- Scope 是否完全一致；
- 对应正式记录是否存在；
- 状态是否为 `Active`；
- 是否是最新版本；
- 是否已过期；
- 是否已遗忘；
- 是否被权限策略禁止；
- 是否符合本次任务目的。

---

## 12.3 排序策略

第一版可以使用：

```text
final_score =
    provider_score
    + importance_weight
    + recency_weight
    + scope_weight
    - contested_penalty
```

其中：

- `provider_score`：Mem0 检索分数；
- `importance_weight`：记忆重要性；
- `recency_weight`：仅对情景记忆明显生效；
- `scope_weight`：项目级精确匹配高于全局用户记忆；
- `contested_penalty`：有争议记录通常直接过滤。

不要对所有记忆统一强衰减。

## 14. 幂等、重试与降级

## 14.1 幂等

建议：

```text
idempotency_key =
tenant_id
+ source_type
+ source_ref
+ content_hash
+ policy_version
```

重复提交同一事件时，不重复创建正式记录。

---

## 14.2 Provider 重试

建议策略：

```text
连接失败：指数退避重试
429：遵循 Retry-After
5xx：有限重试
4xx 参数错误：不重试
超时：最多重试一次
```

外部写入操作必须配合幂等键或本地映射，避免重复记忆。

---

## 14.3 降级策略

Mem0 不可用时：

### 写入

```text
保存 Source
→ 保存 Pending Candidate / Outbox
→ 返回 accepted_for_processing
→ Worker 后续重试
```

### 检索

```text
优先使用本地缓存或 memory_core 中的基础查询
→ 无结果时返回空记忆
→ Agent 继续执行
```

记忆服务故障不应让所有 Agent 请求完全失败，除非任务明确依赖长期记忆。

## 25. 主要风险

### 风险 1：Mem0 自动写入与业务状态不一致

处理：

- Mem0 结果映射为 Candidate；
- Rust 进行状态校验；
- 正式记录在 `memory_core` 中；
- 不直接信任 Provider 返回。

### 风险 2：重复记忆

处理：

- 幂等键；
- `normalized_key`；
- Scope 内查重；
- Provider ID 映射；
- 评测 Duplicate Rate。

### 风险 3：旧事实和新事实同时进入 Context

处理：

- 版本；
- `Superseded` 状态；
- Context 仅选择 Active 最新版本；
- 有争议事实默认不注入。

### 风险 4：跨租户泄露

处理：

- Scope 从认证上下文生成；
- Provider 检索前过滤；
- Rust 检索后二次过滤；
- 数据库查询必须包含 tenant 条件；
- 安全测试。

### 风险 5：Mem0 升级破坏接口

处理：

- Adapter；
- 固定镜像版本；
- OpenAPI 契约测试；
- 测试环境先升级；
- 数据和 Provider 解耦。

### 风险 6：模型费用和写入延迟过高

处理：

- 只提交高价值事件；
- 写入异步化；
- 批处理；
- 使用较小模型；
- 统计每次写入 Token；
- 设置租户配额。

## 27. 最终实现原则

> Mem0 负责“记忆智能”，Rust 负责“系统权威”。

具体来说：

```text
提取、基础去重、向量化、检索。

Rust：
Scope、权限、候选、版本、来源、状态、审计、Context。

PostgreSQL：
保存可迁移、可审计的权威数据。
```

这样既能快速完成 MVP，也不会把整个产品绑定在 Mem0 上。
