我们这次选择的是 Mem0 OSS 自部署。

这个选择并不是因为 Mem0 在所有维度上都最强，而是因为它最符合我们当前的系统边界和开发阶段。

我们已经决定自研 Rust Agent Runtime，包括任务状态、工具系统、权限、上下文组装和执行流程。因此现在需要的是一个可以通过 REST 独立接入的记忆服务，而不是另一套 Agent Runtime。

Mem0 的优势是边界清晰。它主要提供记忆写入、提取、去重、搜索、更新和删除，能够以独立服务的方式接入 Rust 系统。第一版所需的用户偏好、项目事实、跨会话记忆和基础语义检索，它已经能够覆盖。

没有选择 Letta，是因为 Letta 的核心定位是有状态 Agent Runtime。它不仅管理记忆，还管理 Agent、模型、工具、消息和上下文。如果我们只使用它的记忆模块，就无法充分利用它的优势；如果整体采用，又会与自研 Rust Runtime 大量重叠，增加架构绑定和迁移成本。

没有选择 Hindsight，并不是因为它能力不足。相反，Hindsight 在时间检索、图关系、Observation Consolidation、证据追踪和 Reflection 方面比 Mem0 OSS 更完整。但这些能力会带来更复杂的处理链路、后台维护和边界设计。对于当前主要解决用户偏好、稳定事实和跨会话召回的 MVP 来说，复杂度超过了现阶段需求。

所以我们的原则不是选择功能最多的框架，而是选择能够以最低复杂度满足当前核心需求、并且未来容易替换和扩展的框架。

第一阶段使用 Mem0 OSS 快速完成 MVP，同时在 Rust 层保留统一的 Memory Provider 接口、权限、版本、来源和正式状态。未来如果时间推理、经验整合和 Reflection 被证明是核心需求，可以通过 Adapter 引入 Hindsight，或者自研相应模块，而不需要重写 Agent Runtime。

最终结论是：Mem0 负责提供基础记忆智能，Rust Memory Service 保持系统控制权，PostgreSQL 保存权威业务数据。








Letta 的核心优势不只是记忆存储，而是让 Agent 自己管理长期状态。

它会把少量重要信息放在 Memory Block 中，让这些信息每次调用模型时都能被看到；把大量历史内容放在 Archival Memory 中，需要时由 Agent 主动搜索。Agent 在运行过程中还可以自己判断哪些信息值得保存、旧记忆是否需要更新，以及当前任务应该使用哪些历史信息。

所以 Letta 的记忆、上下文和 Agent Loop 是一起工作的。

我们可以把它理解成一个配有秘书的办公室：Memory Block 是桌面上的便签，Archival Memory 是档案室，Agent Loop 是负责整理便签、归档资料和主动查阅历史的秘书。

如果只单独使用 Letta 的记忆模块，就相当于保留了便签和档案室，但没有使用这个秘书。什么时候保存、保存到哪里、什么时候检索、检索结果怎么进入上下文，都需要我们自己的 Rust 系统重新实现。

这样虽然技术上可以使用，但只能发挥 Letta 的部分价值，同时还会引入 Agent、Block、Archive 等 Letta 自己的概念。

因此，Letta 最适合的使用方式是连同它的 Agent Runtime 和上下文管理一起采用。如果我们已经决定自研 Rust Agent Runtime，只需要一个独立记忆服务，那么 Mem0 的边界更清晰、接入更简单，也更容易替换。
